# 阶段 9 的生产改动、记录格式与兼容性

## 候选前端

`scripts/stage4/session.py::run_pair` 在旧会话、候选预检两个边界建立各自的记录目录。Deagle 仍在同一工作目录上处理实际候选。新版前端时钟从准备记录器之前开始，到 GCC 身份再次确认后结束。候选准入、映像哈希、四阶段模型检查、检查点与候选求解仍在原入口执行。[会话入口](../../../scripts/stage4/session.py) · [候选收集器](../../../scripts/stage9/frontend.py)

Linux 上的五次 GCC 分派共用控制器里的 Python 模块。两个标准输入探测完整保存输入、原始输出及退出码。三个文件预处理将 GCC 的标准输出原样传给 Deagle，同时由 GCC 在本次调用中写出 make 依赖。每个文件调用有私有回执 FIFO。包装器等收集器取到生成源码、行标记与实际依赖后才返回，所以临时生成源码在读取期间仍然有效。文件内容的临时记忆只用于一次 GCC 调用，按设备、inode、大小、mtime、ctime 检查稳定性，结束前再检查路径解析。该设计没有会话外常驻记录进程。原始字节和审计文件会占用运行目录空间。[分派脚本](../../../scripts/stage9/dispatch.sh) · [哈希和路径规则](../../../scripts/stage9/provenance.py)

控制器同时等待每次文件通知与前端的 pidfd。到期抛出原有超时异常，由会话退出栈回收进程组。系统没有 pidfd 接口时选用逐调用解释器。系统拒绝为已启动的进程打开 pidfd 时，控制器在同一剩余时间内轮询退出并继续处理文件通知。碰到未知 GCC 参数时执行原记录器，并将该会话标记为不可恢复。GCC 的 stderr、工作目录和原始参数仍随实际调用传递。[旧记录器](../../../scripts/stage3/record_gcc.py) · [退出与超时处理](../../../scripts/stage9/frontend.py)

## 依赖身份

| 既有字段 | 新版对应与校验 |
|---|---|
| `unit` | harness 使用原名字。临时生成单元使用实际源码的 SHA-256，生成源码也保存供复核 |
| `raw_argv`、`argv` | 保留 GCC 原业务参数及原拼写。稳定参数仅替换最后的临时源路径。附加的 `-MD -MF … -MT incdeagle` 仅用于取得同次预处理的依赖清单 |
| `files` | 按原行标记规则记录真实路径及内容哈希。v2 另保存 GCC 列出的先决文件，并要求其覆盖所有实际行标记依赖 |
| `raw_output_sha256`、`output_sha256` | 分别绑定原始 stdout 和只规范化行标记路径后的精确字节。不改写交给 Deagle 的 stdout。v2 再将每条回执和独立保存的原始输出、参数及探测输入核对 |
| `returncode` | 保留实际 GCC 退出值。编译失败进入既有的错误分类和完整回退逻辑 |

v2 还保存两种语言的实际配置探测、GCC 驱动和 cc1/cc1plus 路径与内容、版本、specs，以及相关编译环境变量的内容摘要。环境值按明确的编译器变量名单取摘要。类型布局、目标性质、验证界限及编码工具身份继续由原 manifest 记录。未知来源的行标记使准入拒绝。Deagle 内建的虚拟行标记只在绑定的生成源码确实声明相应标签时承认。

v1 的七字段仍能直接读取。新版将 v2 放进 manifest 的 `context.frontend_dependencies_v2`，重新计算上下文与版本哈希，P0 采集和 P1 绑定共用这一规则。缺少附件、原始输出与记录不符、编译器身份不稳定时，准入给出拒绝原因。拒绝身份还区分 P0 和 P1，原理论审核因上下文不同而拒绝历史子句。旧阶段的归档在各自的固定提交上复核。阶段 9 对正常运行重新建立 P0 会话；新附件没有事后补写到旧证据中。[旧状态取证](../../../scripts/stage9/reference_gcc.py) · [生产差异补丁](../../../patches/stage09-frontend.patch)

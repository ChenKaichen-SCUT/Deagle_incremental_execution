# 阶段 9 候选前端实施方案

本方案在实现和正式计时之前写入。起点为 `edd7386f8674eb5db08593d327256ea874bf05f6`，正式验证对照固定在 `247894bf77904bb34e547b5a636b8afe8527add4`。

阶段 8 观察到两个从标准输入探测 GCC 配置的调用和三个文件预处理。前两次 Python 启动约占 41 ms，后三次经记录器比直接调用 GCC 多用约 96 ms，退出发现再占 14～18 ms。直接执行 GCC 的原生前端仍需约 43～45 ms。准备采用轻量 shell 分派器，并把记录计算放在候选控制器已有的 Python 进程中。预计可减少 100～145 ms，仍需支付实际预处理、依赖读取和进程间通知成本。

- 在 `scripts/stage4/session.py::run_pair` 的候选前端启动和等待边界接入分派器。由 Linux pidfd 通知退出，沿用同一剩余时间与进程组清理。用单会话私有 FIFO 交接 GCC 的实际输出、依赖文件、原始参数和退出码。控制器完成取证后才让 GCC 包装器返回，保证临时生成单元仍然存在。没有跨候选缓存和驻留服务。
- 从 `scripts/stage3/record_gcc.py` 核对并复用行标记规范化规则。保留 v1 的七个字段，以附加记录保存两个真实配置探测和 GCC 同次预处理导出的头依赖。先在受控输入上比对加入 `-MD -MF -MT` 前后的 stdout、stderr 和退出码。原文件参数、宏、生成源码及实际读取文件按内容绑定。复用资格由 P0/P1 完整证据判断。出现未知调用、依赖缺失或工具链变化时拒绝旧缓存。旧版证据仍可独立核验，新旧增强附件不齐全时走保守路径。
- 重点风险包括临时文件寿命、不同拼写的同一头文件、路径转义、宏或 ABI 变化、编译失败、超时和进程退出竞态。使用独立副本覆盖这些情况，先比较两个记录器的字段和字节，再测试生产准入与回退。独立全量结果、四阶段模型、原生计数和历史引理收据为正确性验收依据。
- 五个重点病例对冻结控制器和新控制器分别运行五次普通 F1/I3，按重复号交替，串行执行。前端细分和求解器有序输入在独立诊断组测量。完成后再回归九例并保留两份残错的全部见证。完整周期计入 P0、补丁重放及 P1。所有预测都以实际运行结果验收。
